Part 2: The Core Problem & Our Shift Target: 0:25 – 0:55 (30s)

Breaking Free from Rigid Keyword Skills

Why voice AI needs reasoning and persistent state, not just hardcoded commands.

❌ Traditional Alexa Skills

• Rigid slot filling: Fails if exact phrasing is missed.
• Stateless: Forgets user preferences across turns.
• Fragmented skills: Users must remember specific skill names.
• Purely reactive: Cannot anticipate or proactively update.

✅ The Alexa+ Solution

• Free-form conversational reasoning with Gemini 3.8.
• Contextual Memory Engine: Retains user profiles & past dialogues.
• Unified MCP Server: Connects any tool dynamically.
• Real-time SSE streaming & Web telemetry console.

Part 3: System Architecture Target: 0:55 – 1:30 (35s)

Production Multi-Protocol Architecture

Seamless bridge between Alexa Skills Kit (ASK), Google GenAI, and MCP Standard.

[User Voice Speech / Web Mic] │ ▼ [AWS Lambda / ASK SDK Core] ───► [Contextual Memory Engine (SQLite + Turso)] │ │ (User preferences, past sessions, history) ▼ ▼ [Gemini 3.8 LLM Orchestrator] ◄───────────┘ │ (Structured Pydantic Schemas: Reason ➔ Select Tool ➔ Natural Voice Speech) ▼ [Model Context Protocol (MCP) Server] ├── Tools: alexa_create_booking · alexa_execute_automation · alexa_query_tasks └── Streamable HTTP (SSE) ──► [Interactive Web Console + Alexa Voice TTS]
🎙️ Spoken Script: Read naturally: 35 Seconds

"Here is how our architecture works: Voice requests enter AWS Lambda through the Alexa Skills Kit. Before routing, our system fetches the user's profile and dialogue history from our hybrid SQLite and Turso database. Gemini 3.8 Flash receives this context along with all registered MCP tool schemas. The model returns a structured Pydantic decision, invoking the right MCP tool over JSON-RPC and generating conversational voice speech."
